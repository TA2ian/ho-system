# HO Network — Lovable Handoff Specification

## 1. Purpose

This document defines the presentation and UX boundary for the HO Network web application on branch `foundation/v1`.

Lovable is responsible for improving and implementing the presentation layer, UX, responsive behavior, information hierarchy, interaction design, accessibility, and Arabic RTL visual system.

The existing API, authorization model, accounting rules, financial calculations, idempotency behavior, and persistence model remain authoritative and must not be reimplemented in the client.

## 2. Current foundation

The current web application is a React/Vite PWA in `apps/web`.

Established modules:

- Dashboard / API connectivity
- Customers
- Sales Orders
- Invoices
- Receivables
- Payments
- Delivery navigation shell
- Accounting navigation shell

Operational flows already represented in the foundation:

Customer -> Sales Order -> Confirm -> Invoice -> Issue/Post -> Receivable -> Payment -> Allocation -> Accounting

Reversal-sensitive flows include:

- Invoice void with a required reason
- Payment reversal with a required reason
- Allocation reversal
- Accounting reversal entries generated by the API

Delivery and Accounting currently have foundation placeholders and are not to be represented as fully operational unless their API-backed workflows are implemented.

## 3. Non-negotiable architecture boundary

Lovable must not move business authority into the browser.

Do not implement client-side:

- Authorization decisions
- Permission enforcement
- Resource ownership decisions
- Financial totals as authoritative values
- Accounting posting logic
- Journal-entry generation
- Receivable balance calculation as authoritative state
- Payment allocation rules
- Reversal rules
- Accounting-period rules
- Idempotency semantics
- Server-side validation replacement
- Persistent storage of bearer tokens
- API response caching as offline financial data

The API and PostgreSQL database remain authoritative.

The frontend may display derived presentation values returned by the API, but must not silently replace server values with locally calculated financial state.

## 4. Authentication boundary

The foundation currently accepts an externally issued bearer token and stores it in memory only.

This is a temporary integration boundary.

Lovable should design a clean authentication experience that can later be connected to the selected production identity provider without coupling the UI to a provider-specific implementation.

Do not introduce Local Storage, IndexedDB, or persistent cookies for the current bearer token boundary.

The frontend is never the authorization boundary.

## 5. API integration contract

The existing transport boundary is `apps/web/src/api/client.ts`.

It:

- attaches the bearer token when available
- preserves the API error message contract
- supports relative and absolute API bases
- requires an Idempotency-Key for POST requests
- expects the API to remain authoritative

Use the existing client abstraction rather than creating parallel fetch/axios abstractions.

Do not bypass the existing API contract merely to simplify UI development.

## 6. Information architecture

Primary navigation should remain organized around operational workflows:

1. لوحة التحكم
2. العملاء
3. المبيعات
4. الفواتير
5. الذمم
6. التحصيل والمدفوعات
7. التوصيل
8. المحاسبة

The visual hierarchy should make the business lifecycle understandable without implying that every navigation item is already fully implemented.

## 7. UX principles

The application is Arabic-first and RTL-first.

Requirements:

- Arabic labels and primary content by default
- Correct RTL layout, alignment, spacing, icons, tables, forms, pagination, and navigation
- Latin/numeric identifiers may remain LTR where appropriate
- Phone numbers, email addresses, reference numbers, IDs, dates, and monetary amounts must remain legible
- Avoid decorative complexity that obscures operational information
- Prefer clear status, action, and consequence communication
- Destructive or irreversible-looking actions require explicit confirmation and reason where the API requires one
- Never imply that an action succeeded until the API response confirms it

The design should support desktop and mobile operational use.

## 8. Required state model for screens

Every API-backed screen should have explicit:

- Initial state
- Loading state
- Loaded state
- Empty state
- Validation-error state
- Authorization/permission-denied state
- Authentication/session-expired state
- API/business-rule error state
- Retry path where retry is meaningful
- Mutation-in-progress state
- Mutation-success feedback
- Mutation-failure feedback

Do not hide API failures behind generic empty states.

Do not allow duplicate submissions while a mutation is in progress.

## 9. Customers

The current `foundation/v1` Customer API is intentionally narrower than the long-term HO Network Customer 360 model.

Current API-backed customer capabilities only:
- List active customers
- Pagination
- Create customer
- Individual/business type
- Display name
- One primary phone field
- One email field
- Notes
- Active/inactive/blocked status

The current frontend must not fabricate Customer 360 fields that are not present in the API.

The long-term HO Network customer model is broader because the platform operates around media-buying customer relationships. The target Customer 360 model is documented separately in `docs/customer-360-expansion.md` and is not considered frontend-ready until its server-side contract exists.

When the Customer 360 contract is implemented, the customer experience is expected to organize, as API-backed resources, the following areas:
- Customer profile
- Multiple phone numbers
- Multiple addresses/residence records
- Social accounts
- Notes
- Documents and document references
- Media agreements
- Media campaigns
- Delivery orders
- Invoices
- Payments
- Financial/operational history or timeline

The relationship between media-buying entities must remain server-authoritative:

Customer -> Media Agreement -> Campaign -> advertising platform/account -> planned budget -> actual advertising spend

Customer accounting balance, campaign budget state, and actual advertising spend are distinct concepts and must never be merged into one client-side balance.

Until the corresponding API resources are implemented, Lovable should keep Customers limited to the current contract and may provide navigation placeholders only where explicitly identified as future functionality.

The customer selector should remain reusable by Sales Orders, Invoices, Receivables, Payments, and future media-buying workflows.

## 10. Sales Orders

The sales-order experience should preserve the existing lifecycle:

- Select customer
- Select catalog/product data supplied by the API
- Create order
- View paginated orders
- Confirm order
- Cancel order where allowed

The UI must clearly distinguish draft, confirmed, and cancelled states.

Do not let the client invent lifecycle transitions.

## 11. Invoices

The invoice experience should preserve:

- Creation from a confirmed sales order
- Paginated listing
- Issue/posting
- Guarded void flow
- Required reason where applicable

The interface should distinguish non-posted and posted financial states visually.

Once an invoice is posted, the UI must not suggest that its financial contents can be edited like an ordinary draft.

## 12. Receivables

Receivables are server-derived financial state.

The UI should present:

- Customer receivable view
- Issued invoices
- Invoice total
- Allocated amount
- Outstanding amount
- Pagination
- Allocation/reversal-aware status

Do not recompute the authoritative balance in React.

The displayed balance must come from the API response.

## 13. Payments

The payment experience should support the existing API-backed workflow:

- Record payment
- Paginated payment list
- Allocate payment to invoice
- Reverse payment
- Required reversal reason where applicable
- Clear status and audit-sensitive feedback

Every mutating operation must use the existing idempotency-aware API client.

Do not generate an alternative client-side idempotency protocol.

## 14. Delivery and Accounting

These modules currently exist as navigation/foundation surfaces.

Do not fabricate operational behavior, sample financial data, fake controls, or simulated workflows.

When the corresponding API workflows are ready, the modules can be implemented against those contracts.

## 15. Dashboard

The dashboard should prioritize operational clarity.

It may present:

- API/system status
- Operational summaries backed by real API data
- Financial or workflow KPIs only when backed by authoritative API responses

Do not introduce fake KPI values or client-generated financial summaries.

## 16. PWA and offline behavior

Offline support is shell-only.

The service worker may cache static application assets and use the existing shell fallback behavior.

Do not cache:

- API responses
- Customer financial data
- Invoice financial data
- Receivable balances
- Payment records
- Accounting records

Do not build an offline mutation queue unless a separately specified server-side synchronization design is introduced.

## 17. Accessibility

The redesigned UI should target production-grade accessibility:

- semantic landmarks
- correctly associated labels
- keyboard navigation
- visible focus states
- sufficient contrast
- accessible error messages
- `aria-live`/status handling where appropriate
- dialogs with correct focus management
- tables with meaningful headers
- controls with unambiguous accessible names

Accessibility must remain functional in Arabic RTL mode, not only in an LTR test configuration.

## 18. Responsive behavior

The design must support:

- desktop
- tablet
- mobile

Tables should have an intentional responsive strategy rather than simply overflowing the viewport.

Forms should remain usable on narrow screens.

Primary actions must remain discoverable without requiring horizontal scrolling.

## 19. Visual design direction

Create a professional operations/ERP interface rather than a marketing website.

Prioritize:

- information density without clutter
- strong hierarchy
- predictable actions
- consistent status semantics
- reusable components
- restrained visual decoration
- clear financial presentation
- fast scanning by operators

Use a coherent design system for:

- typography
- spacing
- radii
- surfaces
- borders
- buttons
- inputs
- tables
- badges/statuses
- alerts
- dialogs
- pagination
- empty states
- loading states

## 20. Component architecture

Prefer reusable components and feature-level composition.

Avoid putting business rules into generic visual components.

Suggested presentation primitives:

- AppShell
- Sidebar / navigation
- TopBar
- PageHeader
- StatusBadge
- DataTable
- Pagination
- FormField
- SelectField
- EmptyState
- LoadingState
- ErrorState
- ConfirmDialog
- ReasonDialog
- Toast/StatusFeedback
- MetricCard

Feature modules should consume API data and call the existing API client boundary.

## 21. Financial safety UX

The UI must make state transitions explicit.

For actions such as issue, void, allocate, and reverse:

1. Show the current state.
2. Show the action and its consequence.
3. Require confirmation when the API operation is consequential.
4. Require a reason when the API contract requires it.
5. Disable duplicate submission while pending.
6. Wait for server confirmation.
7. Refresh or reconcile displayed state from the API response.
8. Display the resulting state clearly.

Never claim a financial operation succeeded based only on optimistic local state.

## 22. Forbidden shortcuts

Do not:

- replace the API with mock data
- hard-code financial balances
- create fake authentication
- persist bearer tokens for convenience
- bypass permission errors in the UI
- silently retry non-idempotent mutations outside the existing contract
- create a second API client
- change API routes to suit the visual design
- modify accounting semantics for UI convenience
- cache financial API responses in the service worker
- present placeholders as completed functionality

## 23. Acceptance criteria

A Lovable implementation is acceptable only if:

- Arabic RTL is the default experience.
- Existing API routes and payload contracts remain unchanged unless a separately reviewed backend change is required.
- Existing authorization and financial authority remain server-side.
- Existing idempotency behavior is preserved.
- Customers, Sales Orders, Invoices, Receivables, and Payments remain functional.
- Loading, empty, validation, permission, authentication, and API-error states are explicit.
- No financial API data is persisted by the offline shell.
- Delivery and Accounting are not falsely represented as operational if their workflows are not implemented.
- The interface is responsive across desktop, tablet, and mobile.
- Keyboard and screen-reader semantics are considered throughout.
- Typecheck/build/test/audit remain green after integration.

## 25. Source-of-truth hierarchy

When implementing or resolving ambiguity, use this order:

1. Existing API behavior and server-side business rules
2. OpenAPI/API contract
3. Existing frontend integration behavior
4. This UX handoff specification
5. Visual design preference

Visual preference must never override a higher-level business or security constraint.
